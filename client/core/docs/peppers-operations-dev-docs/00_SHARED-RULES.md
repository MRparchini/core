# Shared implementation rules

These rules apply to every Peppers Operations DEV module.

## Project paths

- GitHub repository: `MRparchini/core`
- Default branch: `main`
- Frontend: `./client/core`
- Frontend documentation: `./client/core/docs`
- Apps Script backend: `./server/appScripts`
- Apps Script source: `./server/appScripts/src`
- This documentation bundle: `./client/core/docs/peppers-operations-dev-docs`

## Work method

1. Run Codex from the repository root, where the `client` and `server` folders are visible.
2. Read `./client/core/AGENTS.md`, inspect the existing architecture and inspect the current git diff before editing.
3. Treat Customers, Products and Menus as existing services. Extend or repair them; do not rebuild them without evidence that a rewrite is necessary.
4. The MenuItems worksheet already contains headers/data, but no MenuItems service was present in the inspected GitHub source. Create that service from the existing Customers, Products and Menus patterns while preserving live data.
5. Use existing naming, API response, error-handling, routing, component and styling conventions where they are sound.
6. Implement only the module named in the selected worksheet document.
7. Do not create unrelated modules, abstractions or infrastructure.
8. Preserve unrelated user changes and working behaviour.

## Google Sheets rules

1. The spreadsheet is named exactly `Peppers Operations DEV`.
2. Use the shared `SPREADSHEET_ID` configuration already used by the application.
3. Create one service-specific config file per module for the sheet name, exact headers, allowed values and pagination limits.
4. Do not duplicate `SPREADSHEET_ID` inside service-specific config files.
5. Follow the existing service-config pattern: one-based `COLUMNS`, `TOTAL_COLUMNS`, and an exact `HEADERS` list where appropriate.
6. Validate the complete header row before reading or writing data. Return a clear configuration error if required headers are missing or out of order.
7. Do not refactor all working services merely to introduce a new column-mapping system.
8. Do not automatically rename, insert or delete live worksheet columns unless the task explicitly authorises a sheet migration.
9. Preserve existing rows and unknown columns.
10. Use batch reads and writes where practical; avoid one spreadsheet call per cell.

## Data rules

1. New internal IDs use UUID strings generated by the backend.
2. Existing legacy IDs must never be changed or renumbered.
3. Store timestamps as UTC ISO 8601 strings.
4. Preserve `CreatedAt` during updates and refresh `UpdatedAt` only after a successful change.
5. Store money as integer pence. Never store operational money as floating-point pounds.
6. Trim ordinary text, but do not remove meaningful spaces inside names or addresses.
7. Telephone numbers, postcodes, Clover IDs, SKUs and codes are text, never numeric calculations.
8. Validate all input in the backend even when the frontend also validates it.
9. Return consistent success, validation, not-found and unexpected-error responses.
10. Prefer deactivation over physical deletion when another worksheet can reference the record.

## API and frontend rules

1. Follow the existing service transport pattern instead of inventing a second API style.
2. Add loading, empty, success and error states to management pages.
3. Use pagination only for lists that can grow significantly.
4. Add search only to fields that a real user is likely to search.
5. Do not expose raw spreadsheet row numbers as stable record IDs.
6. Do not trust totals, prices, IDs or timestamps sent by the browser; calculate or validate them in the backend.
7. Keep the interface usable on a normal desktop and a phone-sized screen.

## Security rules

1. Never store Clover OAuth tokens, API keys, passwords or card details in Google Sheets, committed source files or Markdown documents.
2. Use the repository's existing safe environment/configuration mechanism or Apps Script Properties for secrets.
3. Never log secrets or full payment-card data.

## Completion rules

Before reporting completion:

1. Run the relevant frontend build, type check, lint and tests that exist in the repository.
2. Run available backend tests or safe local checks.
3. Exercise create, read, update, list/search and deactivate flows where applicable.
4. Review the final git diff for accidental or unrelated changes.
5. Report every file created or changed.
6. Report any unverified behaviour or remaining issue plainly.
