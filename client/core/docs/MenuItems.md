# MenuItems Service

## Goal and domain definition

`MenuItems` is the relationship between `Menus` and `Products`. It controls where a product appears, the menu-specific presentation text, the base menu price, display order, and local active state.

A `MenuItem` is not a `Product`, `ProductVariant`, `Modifier`, order line, or Clover inventory mapping. `Products.Category` must not be used as the menu relationship.

## Worksheet

Use a worksheet named exactly:

`MenuItems`

Columns must be in this exact order:

1. `ID`
2. `MenuID`
3. `ProductID`
4. `DisplayName`
5. `DescriptionOverride`
6. `BasePricePence`
7. `SortOrder`
8. `IsActive`
9. `CreatedAt`
10. `UpdatedAt`

If the worksheet is empty, the backend may initialize the header. If an existing non-empty worksheet has an incompatible header, the backend must return an error and must not overwrite existing data.

## Field rules

`ID` is required, unique, immutable, and generated by Apps Script with `Utilities.getUuid()`.

`MenuID` is required and must reference an existing row in `Menus`. The referenced menu may be inactive.

`ProductID` is required and must reference an existing row in `Products`. The referenced product may be inactive.

`DisplayName` is an optional trimmed string. When empty, the effective display name is `Product.Name`. Do not automatically copy the product name into this column.

`DescriptionOverride` is an optional trimmed string. When empty, the effective description is `Product.Description`.

`BasePricePence` is required and must be a non-negative integer.

`SortOrder` is a non-negative integer and defaults to `0`.

`IsActive` is boolean and defaults to `true`. Deactivation preserves the row.

`CreatedAt` and `UpdatedAt` are ISO 8601 timestamps generated by the backend. Updates preserve `CreatedAt` and refresh `UpdatedAt` whenever a mutable field changes.

## Relationship rules

The stored `MenuID` and `ProductID` pair must be unique across active and inactive rows.

If an inactive relationship already exists, creation must be rejected as a duplicate. The caller should reactivate or edit the existing `MenuItem`.

MenuItem rows must never be physically deleted. `delete` is a backward-compatible alias for deactivation.

## Effective availability

Effective availability is derived at read time:

```ts
menuItem.isActive && menu.isActive && product.isActive
```

Do not store effective availability in the worksheet.

## Money storage

Store money as integer pence, not a decimal string. For example, GBP `12.95` is stored as `1295` in `BasePricePence`.

The frontend accepts normal GBP input such as `12.95`, converts it to pence before sending it to the backend, and displays prices with `Intl.NumberFormat` using `en-GB` and `GBP`.

## Backend API

Use service aliases `menuItem`, `menuItems`, and `menu-items`; all normalize to the MenuItems service.

GET actions:

- `getAll`: list menu items.
- `search`: alias of list with a query.
- `getById`: requires `id`.

POST actions:

- `create`: requires `menuItem` with `menuId`, `productId`, `basePricePence`, and optional mutable fields.
- `update`: requires `id` and `menuItem` fields to update.
- `activate`: requires `id`.
- `deactivate`: requires `id`.
- `delete`: requires `id`; performs deactivation, not row deletion.

List parameters:

- `page`
- `pageSize`
- `query` or `search`
- `menuId`, `menuID`, or `MenuID`
- `productId`, `productID`, or `ProductID`
- `active`, `isActive`, or `status` for local active status
- `effectiveActive`, `effectiveIsActive`, or `effectiveStatus` for derived availability

## Response shape

List responses keep the existing API structure:

```ts
{
  success: true,
  count: number,
  total: number,
  page: number,
  pageSize: number,
  totalPages: number,
  hasPreviousPage: boolean,

```

Each `MenuItem` contains stored fields plus derived fields:

```ts
  basePricePence: number,

  productName: string,
  kitchenName: string,
  productIsActive: boolean,
  effectiveDisplayName: string,
  effectiveDescription: string,
  effectiveIsActive: boolean
}
```

## Frontend requirements

The frontend management page lives at `/menu-items` and includes:

- Paginated MenuItems table.
- Debounced search.
- Menu filter.
- Local status filter.
- Effective availability filter.
- Create and edit forms.
- Activate action.
- Deactivate action with confirmation.
- Loading, empty, error, and success states.
- Refresh action.

The form uses Menu and Product selectors and must never ask the user to type raw UUID values. Active Menus and Products are shown by default, while existing inactive references still display when editing old records.

The table shows Menu name, Product name, effective display name, kitchen name, base price in GBP, sort order, local status, effective availability, and actions.

## Search, filters, sorting, and pagination

Search matches:

- effective display name
- stored `DisplayName`
- `Product.Name`
- `Product.KitchenName`
- `Menu.Name`

Filters support MenuID, ProductID, local active status, and effective active status.

Sort list results by:

1. `Menu.SortOrder`
2. `MenuItem.SortOrder`
3. effective display name

The backend must load required Menu and Product rows once per request, build ID lookup maps, and join in memory. It must not perform one Google Sheet read per MenuItem.

## Soft deactivation

MenuItems are never physically deleted. Deactivation sets `IsActive` to `false` and preserves the row. Activation sets `IsActive` to `true`.

Product deletion is also soft deactivation so MenuItems can keep stable Product references.

## Validation and error codes

Backend validation is authoritative. Frontend validation is not sufficient.

Expected errors:

- `400`: invalid input, invalid filters, missing IDs, invalid header, invalid MenuID, invalid ProductID, invalid pence value, invalid sort order.
- `404`: requested MenuItem, Product, or Menu record not found where applicable.
- `409`: duplicate `MenuID` and `ProductID` relationship.
- `500`: unexpected failure.

Successful responses must not break existing Customers, Products, or Menus response shapes.

## Scope exclusions

Do not implement in this task:

- ProductVariants
- ModifierGroups
- Modifiers
- ProductModifierGroups
- Orders
- OrderItems
- Clover API integration
- Authentication redesign
- Spreadsheet migration
- Deployment

Clover IDs must not be added to `MenuItems` in this task.

Do not rename or delete existing worksheets.

## Manual verification checklist

- Header initialization on an empty `MenuItems` worksheet.
- Incompatible non-empty header returns a clear error and does not overwrite data.
- Create a MenuItem with valid `MenuID`, `ProductID`, GBP price converted to pence, and optional display fields.
- Duplicate `MenuID` and `ProductID` creation returns `409` and advises reactivation/editing.
- Invalid `MenuID` returns `400`.
- Invalid `ProductID` returns `400`.
- Get by ID returns stored and derived fields.
- Search matches effective display name, stored display name, Product name, Kitchen name, and Menu name.
- Filters work for MenuID, ProductID, local active status, and effective active status.
- Pagination returns correct totals and page metadata.
- GBP `12.95` is stored as `1295` and displayed as GBP.
- Update preserves `CreatedAt`.
- Update changes `UpdatedAt`.
- Deactivating the parent Menu changes child `effectiveIsActive` to `false`.
- Deactivating the parent Product changes child `effectiveIsActive` to `false`.
- MenuItem activation sets local `IsActive` to `true`.
- MenuItem deactivation sets local `IsActive` to `false`.
- Delete alias deactivates the row rather than deleting it.

## Future relationships

`MenuItems` provides the menu placement and base price layer. Future `ProductVariants`, `ModifierGroups`, `Modifiers`, `Orders`, and `OrderItems` should reference the normalized catalog/order model rather than duplicating MenuItem data. Future Clover work should be handled in a separate mapping or integration layer, not by adding Clover IDs to `MenuItems` in this task.
